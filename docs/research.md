## Целевое поведение

В текущей версии для macOS реализована процессная пауза для выбранных `.app`, Codex CLI и Claude Code. Панель предлагает доверять обнаруженному адресу VPN после сверки источников. Решения по IP и переходы паузы хранятся в локальном журнале.

При падении монитора отдельный процесс оставляет записанные паузы в силе и запускает новый монитор. Тот возобновляет процессы после свежей проверки соответствующего правила. Тест `python3 scripts/test-process-recovery.py` проверяет падение монитора, отказ помощника, конкурирующий запуск, повреждение журнала и независимое применение правил к пересекающимся деревьям.

По публичному описанию Kordon при первом запуске предлагает подтвердить, что обнаруженный IP принадлежит VPN. После смены маршрута выбранные процессы и их потомки замораживаются до проверки. Kordon параллельно опрашивает источники IP, отдельно проверяет IPv6, а DNS и маршруты к сервисам ИИ показывает в диагностике. Его отдельная команда `kordon run` проверяет адрес до запуска команды и может остановить её по таймеру. В MySafeAI есть свой запуск `mysafeai run`, отдельные правила, диагностика маршрутов до сервисов и режим системного прокси. Условия и ограничения описаны в [руководстве](../README.md#проверка-подключения). [Первый запуск Kordon](https://github.com/ef1m03/kordon#первый-запуск) · [Режимы CLI](https://github.com/ef1m03/kordon#команды-в-терминале)

1. Пользователь выбирает приложения или запускает Claude Code либо Codex CLI в изолированном окружении. Локальная политика задаёт допустимый интерфейс и, при необходимости, IP выхода.
2. Применение политики запускается до первого соединения. При потере VPN выбранный трафик блокируется, пока условия снова не будут подтверждены. Прямой трафик остальных приложений продолжает работать.
3. Основная карточка показывает, включена ли блокировка, какой маршрут проверен и почему приложение ограничено. Диагностика отдельно показывает IPv4, IPv6, DNS и маршруты до конкретных сервисов. В режиме split tunneling одного маршрута по умолчанию недостаточно для вывода о Claude или Codex.

Для проверки будущей блокировки нужны TCP, UDP/QUIC, IPv4, IPv6, DNS, уже открытое соединение, дочерний процесс, старт без VPN, смена Wi-Fi, сон и падение управляющего процесса. Критерий для сетевой реализации — выбранный трафик отсутствует на прямом интерфейсе во время переключений.

## Платформы

- **macOS.** Первый интерфейс — нативное окно SwiftUI. Для блокировки потоков приложений требуется проверить прототип [Network Extension Content Filter](https://developer.apple.com/documentation/networkextension/nefilterdataprovider), включая подпись, активацию и классификацию дочерних процессов CLI. Привязка к туннелю, DNS и уже разрешённые соединения требуют отдельных испытаний.
- **Windows.** Трей и [Windows Filtering Platform](https://learn.microsoft.com/en-us/windows/win32/fwp/windows-filtering-platform-start-page) для правил по приложениям. Проверить применение к дочерним процессам и идентификацию VPN-интерфейса.
- **Linux.** Для первого CLI-режима проверить [отдельное сетевое пространство WireGuard](https://www.wireguard.com/netns/) с туннелем как единственным внешним интерфейсом. Графические приложения и CLI могут использовать общую политику, когда их трафик действительно проходит через соответствующий платформенный механизм.

## Опциональный бот

Desktop-приложение не зависит от Telegram. Если нужен пульт, пользователь разворачивает отдельный бот на своём устройстве или сервере и привязывает его к своему компьютеру. Предлагаемый первый сценарий — уведомления о состоянии сети и запрос статуса. Доступ к результатам Claude Code или Codex добавляется отдельно и только для выбранной сессии.

Привязка должна быть явной, с одноразовым кодом, закреплённым идентификатором чата и возможностью отключения на компьютере. Секреты хранятся у владельца. Каналу не нужны произвольные команды терминала, системные настройки или доступ ко всей истории. Если пользователь включает пересылку фрагмента ответа, этот фрагмент проходит через Telegram. См. [Telegram Bot API](https://core.telegram.org/bots/api).

## Проверка адресов

В [awesome-console-services](https://github.com/chubin/awesome-console-services#ip-address) перечислены AWS, ipify, IPinfo, ident.me и DNS-запросы Cloudflare. Встроенный набор MySafeAI использует HTTPS и сохраняет пользовательские источники. Для IPv4 по умолчанию выбраны AWS и Cloudflare. Для проверки IPv6 используются ident.me и отдельный [IPv6 endpoint ipify](https://www.ipify.org/). При отсутствии IPv6-маршрута запросы к ним пропускаются. Исторические настройки с AWS и Cloudflare получают оба IPv6-источника при миграции, пользовательские наборы сохраняются.

Одинаковый ответ требуется от двух разных хостов для каждой используемой версии IP. Разные пути на одном хосте считаются одним источником. Эта проверка снижает зависимость от единичного ошибочного ответа. Разные DNS-имена могут иметь общего оператора или инфраструктуру, поэтому пользовательские сервисы требуют осмысленного выбора.

Системная диагностика читает `scutil --dns` и проверяет маршруты до основных резолверов через `route -n get`. Локальный stub resolver оставляет путь неопределённым. Опциональная пауза срабатывает при обнаруженном выходе резолвера через внешний интерфейс или другой туннель.

## Дополнительные меры безопасности и удобства

1. Проверять фактический выход прямых и системных запросов. В [метриках URLSession](https://developer.apple.com/documentation/foundation/urlsessiontasktransactionmetrics/isproxyconnection) есть признак использования прокси. В MySafeAI он используется вместе с двумя IP-источниками для каждого пути. Настроенный PAC может выбирать прямой выход для отдельных адресов, поэтому одно наличие прокси в настройках не определяет путь запроса.
2. Наблюдать реальные рекурсивные DNS-серверы на уникальных именах. По запросу пользователя MySafeAI получает идентификатор теста у [bash.ws](https://bash.ws/dnsleak), формирует имена в его зоне и читает список резолверов. Запросы выполняются через системный DNS API macOS с ограничениями по количеству, времени и размеру ответа. Отчёт дополняет диагностику. Операторы и anycast-география требуют интерпретации с учётом выбранного DNS. [Mullvad объясняет](https://mullvad.net/en/help/split-tunneling-with-the-mullvad-app), почему сторонний DNS может идти внутри VPN и при этом называться утечкой в проверке провайдера.
3. Следующим этапом защиты стоит проверить Network Extension с [NEFilterDataProvider](https://developer.apple.com/documentation/networkextension/nefilterdataprovider) для обработки сетевых потоков и правил по приложениям. Нужны прототип, подпись, entitlement и испытания TCP, UDP/QUIC, DNS и уже открытых соединений. Процессная пауза сама по себе не отзывает переданные ядру пакеты.
4. Добавить диагностику конкретных сервисов и маршрутов к их адресам. [TunnelCrack](https://www.usenix.org/conference/usenixsecurity23/presentation/xue) показывает риски исключений маршрутизации для локальных сетей и адреса VPN-сервера. План проверки должен включать обнаружение внешнего маршрута к нужному сервису и IPv6, поведение при смене Wi-Fi и пробуждении. Проверки следует выполнять на собственном подключении.
5. Добавить понятный автозапуск при входе в macOS через [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), экспорт обезличенного отчёта и браузерную диагностику WebRTC. Для браузерного WebRTC требуется проверка внутри самого браузера, поскольку его DNS over HTTPS и сетевые настройки могут отличаться от нативного приложения.

[VPNalyzer](https://censoredplanet.org/papers/vpnalyzer.pdf) содержит измерения утечек DNS и IPv6 при обрыве туннеля и подтверждает необходимость отдельных испытаний восстановления соединения. Предложенный порядок продолжения — сетевой фильтр и сервисные маршруты, затем автозапуск и безопасный экспорт отчёта.
